SI-Universal-Agent

A super-intelligent agent anyone can direct, held inside a harness that keeps it predictable.

Discussion Opened 11 Nov 2026 Owner: Christopher Hamm Artifacts: 9 UI screenshots from the harness prototype

Unlisted working page. Positions here are drafts to argue with, not decisions.

The idea in one paragraph

An everyday person in Sales, Finance, HR, or Support types what they want done and how often. They never see a prompt, a model picker, or a workflow editor. The harness matches the request to a workflow someone has already built and published, fills in the few settings that user is allowed to touch, locks the rest, and shows the plan before anything runs. Agents with named personas do the work stage by stage. A human approval gate pauses the run before anything leaves the building. Every run is visible, logged, and repeatable.

"Super intelligent" is deliberately not the interesting part. The models will keep getting smarter on their own. The part worth designing is the harness: the structure that turns raw capability into something an ordinary team can trust on a Monday morning.

Principles the prototype already commits to

  • Plain words in, no settings. The everyday user's whole interface is a text box and a review screen.
  • Two roles, two tools. Everyday users pick jobs. The harness team builds and publishes workflows. Neither sees the other's controls.
  • Locked versus yours. Every setting declares who may change it. The approval guardrail cannot be turned off by the user.
  • Personas, not prompts. Work is assigned to a named role with a model tier and a toolset, so the same persona behaves the same way across workflows.
  • Typed handoffs. Stages pass declared outputs (leads[], company_summary, draft_email, approved_drafts[]). Nothing is passed by vibe.
  • A gate before the world. Nothing is sent, posted, or written back until a person decides.
  • Runs are first-class. Every run has a log, a stage timeline, counts of model calls and human decisions, and a re-run-from-here button.

How this fits a static GitHub Pages site

This site is static files served by GitHub Pages from a public repository. There is no server, no database, no secrets store, and no way to run code on request. That rules some things out and makes others surprisingly natural.

Can live here

  • The simulator. Screens 4 to 9 are client-side with simulated data. They could ship as plain HTML and JavaScript in this folder, no backend needed.
  • Published workflow definitions. Stages, personas, processes, and handoffs as JSON or Markdown files, versioned by git.
  • Design artifacts and this discussion. Screenshots, briefs, decision log.
  • Read-only run reports. A runtime elsewhere could commit a run log as a static page after the fact.

Cannot live here

  • Real runs. Model calls, CRM lookups, and email need a runtime with credentials.
  • Schedules. "Mondays at 7:00 AM" needs something that wakes up.
  • Private data. Anything committed is public, even on an unlisted page.
  • The approval gate itself. A decision has to be recorded somewhere that can act on it.

A plausible split

The site is the publishing surface and the spec. Workflow definitions, persona definitions, and the simulator live here, in the open, as the thing people can read and try. The runtime lives somewhere else: a local agent session on a laptop for one person, GitHub Actions on a schedule for a small team, or a hosted service for anything real. The runtime reads the published definitions from this repo and writes nothing back except, optionally, a run report as a pull request.

That split is itself a harness principle. The published workflow is a git-versioned artifact with a review step. "Publish v4" in the builder could literally be a merged pull request.

Things to argue about

  • The fit score. The prototype matches a job to a workflow at 96% fit. What happens at 70%? Does the harness refuse, ask a clarifying question, or pick the nearest workflow and say so? The honest answer for an everyday user is probably "ask one question, then show the plan."
  • Approval fatigue. Fourteen drafts waiting on Monday morning is fine once. Fourteen every Monday across four agents becomes rubber-stamping, and a gate that is always approved is not a gate. "Approve unflagged, skip flagged" is the right instinct; the QA persona is what makes it safe.
  • The harness team as bottleneck. Everyday users cannot edit workflows by design. That means the harness team's backlog is the ceiling on what the organization can automate. The Processes library (reusable steps) is the pressure valve, but someone still has to assemble them.
  • Cost visibility. Fifty-six model calls for fourteen leads. The counter is shown, but not the dollars, and not the trend. Runs probably need a budget the same way they have a schedule.
  • "Super intelligent" versus "well harnessed." Most of the value in the screenshots comes from structure, not model quality. A smarter model inside the same harness makes each persona better; it does not change the shape. Is the SI prefix a goal, a marketing word, or a warning label?
  • What the agent remembers. Nothing in the prototype shows memory across runs. Does the Researcher persona learn that a company was already contacted in March? That is the CRM's job today, but a universal agent will be asked to remember things the CRM does not hold.

Open questions

  1. Who is the first real user: a single person automating their own week, or a team with a harness owner?
  2. Should the simulator be built out here as a working static demo, and if so, is it a teaching tool or a sales tool?
  3. What is the minimum workflow definition format that both the builder UI and a runtime could read? JSON, YAML, or Markdown with front matter?
  4. Where does the approval gate's decision get recorded so that the runtime can act on it without the site having a backend?
  5. What does a persona definition contain beyond a name, a model tier, and a toolset? Voice sample, constraints, examples, evaluation set?
  6. How does a workflow version get retired when twelve agents depend on it?
  7. What is the failure story? The Runs screen has a "Needs a fix" count of one. What did the user see, and what could they do about it without the harness team?
  8. Does any of this need a server at all for the single-user case, or is a local agent session plus this repository enough?
